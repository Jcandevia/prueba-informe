1. Resumen Ejecutivo

GESKUL 2.0 es una plataforma de software como servicio (SaaS) diseñada bajo una arquitectura Multi-tenant (Multi-inquilino) con capacidad de Marca Blanca. El sistema permite que múltiples instituciones educativas utilicen la misma infraestructura tecnológica manteniendo un aislamiento estricto de sus datos mediante políticas de seguridad a nivel de base de datos.

Stack Tecnológico Principal

  • Frontend: Next.js 16 (App Router, Turbopack).
  • Backend/DB: Supabase (PostgreSQL 15+).
  • Seguridad: Supabase Auth + RLS (Row Level Security).
  • Realtime: Supabase WebSockets.
  • Estructura: Monorepo gestionado con pnpm (apps/web, packages/types).

2. Estado Actual de Desarrollo

A la fecha, el equipo de ingeniería ha completado la cimentación de la arquitectura base del proyecto, logrando la interconexión exitosa entre el frontend y el motor de base de datos local. Los hitos técnicos superados incluyen:

1. Configuración de Monorepo y Paquetes

Se estableció una arquitectura de monorepo utilizando pnpm workspaces. Se aislaron las dependencias dividiendo el proyecto en apps/web (aplicación principal) y packages/types (tipados compartidos).

2. Resolución de Conflictos TypeScript

Se calibró el compilador mediante la purga del archivo tsconfig.json. Se habilitaron banderas críticas como allowJs: true, skipLibCheck: true, y moduleResolution: "bundler", eliminando errores de importación cruzada entre los paquetes del workspace.

3. Despliegue de Base de Datos Local (Supabase)

Se inicializó un contenedor local de Supabase mediante npx supabase start. Se estableció la conexión mediante variables de entorno (NEXT_PUBLIC_SUPABASE_URL y ANON_KEY), validando el acceso a Supabase Studio en el puerto 54323.

4. Next.js 16 SSR & Renderizado Asíncrono

Se solucionó el error de pre-renderizado estático (Blocking Route Error) provocado por el conflicto entre cacheComponents y force-dynamic. La arquitectura se migró exitosamente al uso de React Suspense para la obtención de datos asíncronos limpios desde la tabla de instituciones.

3. Modelo Entidad-Relación (MER)

Diseño normalizado en Tercera Forma Normal (3FN). Todas las tablas maestras heredan la llave foránea institution_id para garantizar el aislamiento criptográfico por inquilino mediante Row Level Security.

5. Arquitectura Operativa y de Seguridad

A. Aislamiento Estricto de Datos (RLS)

La seguridad no depende de filtros en el backend, sino de políticas nativas del motor PostgreSQL. Al autenticarse, Supabase genera un Token JWT. PostgreSQL intercepta cualquier consulta y evalúa la política definida. Ejemplo real en el código:

-- Política de seguridad a nivel de fila (RLS)
CREATE POLICY "Aislamiento Institucional Estricto"
ON grade_records
FOR SELECT USING (
  institution_id IN (
    SELECT institution_id FROM user_profiles
    WHERE user_profiles.id = auth.uid()
  )
);

B. Motor de Marca Blanca (Enrutamiento Dinámico)

El middleware de Next.js captura el parámetro slug (ej. /cotediba). Consulta la tabla institutions, inyecta el JSONB de theme_config como variables CSS y renderiza la aplicación con la identidad visual exclusiva del colegio.

C. Ciclo de Vida: Notificaciones Realtime

  1. El docente inserta una calificación (score = 4.5).
  2. Un Trigger (PL/pgSQL) detecta el INSERT, cruza la tabla student_guardians y crea un registro en notifications para el acudiente principal.
  3. Supabase Realtime captura la mutación y la emite vía WebSockets.
  4. El dispositivo del padre recibe la alerta instantánea con la marca visual del colegio.
